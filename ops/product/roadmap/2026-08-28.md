## 2. FATAL FLAG is leaking rubric-internal language into the exact sentence the report calls its
   "strongest line"

`CLAUDE.md`'s non-negotiable rules say: "Do not expose LLM internals (BARS scoring logic, rubric
weights, signal IDs) in user-facing copy." The PRD table marks Fatal Flag "✅ Done." Both of those are
true of the mechanism's *scoring logic* — but not of its *user-facing text*.

In `app/api/interview/debrief/route.ts`:

```
debrief.summary.overall_impression =
  `[FATAL FLAG] ${Math.round(fatalFlag.skipRate * 100)}% of questions received zero-signal responses. ` +
  debrief.summary.overall_impression;
```

`overall_impression` is not a buried field. Per `components/DebriefReport.tsx` (lines 543-551), it's
written in the interviewer's first-person voice and deliberately "made the visual centerpiece of the
banner per direct feedback that this line is the strongest sentence in the report" — rendered
unescaped, in quotes, as the first thing a user reads after the verdict badge.

So: any session that trips the fatal-flag threshold shows the user a quote that opens with literally
`[FATAL FLAG] 45% of questions received zero-signal responses.` — internal mechanism name, internal
metric name, and a diagnostic-log register, stapled onto the front of what's supposed to read as a
human interviewer's verdict. This both breaks the voice the whole report is designed around and
exposes exactly the class of internal scoring language the non-negotiable rule exists to keep out.
"Fatal Flag" isn't one of the three literally-named terms in the rule (`hire_probability`/BARS/rubric
internals), but "zero-signal" is rubric-internal vocabulary (`lib/fatal-flag.ts`'s own term for its
detection logic) and "FATAL FLAG" is the internal name of a scoring override mechanism — I think this
falls squarely inside the rule's intent, not just its letter.

**This is the item I'd prioritize highest out of everything in this review.** It's live, it's user-
facing, it directly touches the one rule this org has called out as non-negotiable independent of any
department, and unlike the round-type issue below it likely affects real users today (any No-Hire-
via-fatal-flag session), not just legacy data.

I'm not fixing this myself — it's a one-line code change but it's in `lib/groq.ts`/the debrief route,
which is outside this seat's Write-tier (docs only). Flagging for Tech with enough specificity to fix
directly: strip the `[FATAL FLAG] ... zero-signal responses.` prefix from what's shown in
`overall_impression`, and if the fatal-flag signal needs to reach the user at all, phrase it in the
same plain-language register as the rest of the ICP-first copy pass (e.g., something like "Several
answers didn't give me enough to evaluate" — no mechanism name, no jargon).

## 3. Round-type normalization: not unified, and the disagreement is a real stuck-session bug, not just
   a data-quality inconsistency

Analytics' framing (per this brief, corroborated independently in `BACKLOG.md`'s own 2026-08-27 entry)
treated this as "the debrief route and question route don't agree on old `screening`/`technical`
values." That's correct as far as it goes, but I want to sharpen the product read, because I don't
think it's just a data-hygiene issue — it can permanently strand a real session.

Current code, read directly:

- `app/api/interview/question/route.ts`'s `normalizeRoundType()` folds legacy `"technical"` →
  `"technical_screen"` → **5** total questions. Once 5 are answered, the question route returns
  `{ done: true }` and stops issuing questions.
- `app/api/interview/debrief/route.ts`'s own inline normalizer keeps `"technical"` as its own legacy
  key mapped to **8** total questions in its `QUESTIONS_BY_ROUND`. Its completeness gate requires
  `qas.length >= totalQuestions` before it will generate a report at all.

For any session with `round_type` stored as the literal legacy string `"technical"`: the question flow
stops at 5 answers, but the debrief flow will refuse to generate a report until 8 exist. There is no
path for that session to ever reach 8 — it's a dead end, and the user gets a 422 "interview incomplete"
response forever. (`"screening"` doesn't have this problem — both files agree it's 5.)

**Scope check, so this doesn't get overweighted:** the current `SetupForm.tsx` round-type dropdown
(`ROUND_TYPES`) only ever writes `"Technical Screen"`, `"Technical Deep Dive"`, etc. — never the bare
legacy string `"technical"`. So this only affects sessions created before the current taxonomy existed
(pre-dating this round of work), not anything a live user creates today. Given the product is
pre-launch/pre-revenue, that population is probably small or entirely internal test data — but I don't
have a way to query the DB from this seat to confirm the actual count, and "probably small" isn't the
same as "zero," so I'm not marking this as safe to ignore.

**The actual product question Analytics' framing was really asking, and my answer:** should the fix be
(a) reconcile the two normalization maps into one shared helper (the "clean" fix, previously
deliberately not done — BACKLOG.md says so explicitly, "didn't want to guess at something with real
Fatal-Flag-threshold implications"), or (b) backfill the handful of affected legacy rows to a current
`round_type` value and let the maps diverge on paper since nothing will ever hit the divergent branch
again?

My recommendation: **do both, in this order** — backfill first (removes the live stuck-session risk
immediately, is reversible, and doesn't require deciding anything about future behavior), then
consolidate the two normalization maps into one shared helper as a follow-up cleanup once there's no
live data depending on the old branch's behavior. Doing the backfill first also removes the exact
ambiguity that stopped this from being fixed already — once no real row has `round_type = "technical"`
or `"screening"`, unifying the maps is a pure refactor with no behavior-preserving tightrope to walk.
This is a product/data call (what happens to old rows), not just an engineering one, which is why I'm
recording an explicit recommendation here rather than leaving it as "flagged, not touched" a second
time. The actual backfill is a production DB write — Article II-gated, Anshuman's call, not mine or
Tech's to just run.

## 4. Forming my own view on CLAUDE.md's self-flagged "unverified" items

CLAUDE.md already lists four things it isn't sure are actually working live. Rather than restate them,
here's a risk read on each, since that's the actual ask:

- **Preview-analysis Groq call (`InteractivePreview`) — real open risk, highest of the four.** This is
  the first real product interaction a signed-out visitor has with PrepSignals — it's supposed to be
  the proof-of-value moment before asking for signup. It has never once successfully completed in any
  environment it's been built in (sandbox egress blocks `api.groq.com` outright). The wiring around it
  (loading/error/rate-limit states) is verified, but the actual payload — the thing that's supposed to
  make someone believe the product works — is not. If it silently degrades to the generic error state
  for a real visitor, that's a worse first impression than not having the feature at all, because it
  reads as "this product is broken" rather than "this product doesn't have a live demo." I'd want this
  smoke-tested against a real `GROQ_API_KEY` from a non-sandboxed environment before leaning on it as a
  conversion element in anything I write about the product externally.
- **SetupForm signed-out final CTA render — real open risk, same category.** This is the literal last
  step before either a signup or a login for an anonymous visitor who's already invested three form
  steps. If `!isLoaded` doesn't resolve the way the code assumes, or the CTA text/routing has any bug,
  the cost is a fully-warmed-up, about-to-convert visitor hitting a dead end at the most expensive point
  in the funnel to lose someone. Same verdict as above: verify live before treating the ungating work as
  actually closing the loop it was built to close.
- **Debrief-generation-failure fix root cause — acceptable for now.** Unlike the two above, this isn't
  a first-impression surface, and the fix already did real diagnostic work even under uncertainty: it
  quantified the token math that plausibly explains the original bug, and — more importantly — it added
  logging and a specific `debrief_generation_failed` event with a reason code regardless of whether the
  root-cause guess is right. That means even if this exact fix doesn't fully resolve it, the next
  failure won't be silent the way the original one was. I'd deprioritize re-verifying this relative to
  the two items above.
- **Mobile responsiveness (static-analysis only) — real open risk, and arguably underweighted given who
  the ICP is.** The ICP-first redesign explicitly targets young professionals / college students in the
  India market — a population that skews toward mobile as a primary or only device far more than a
  general SaaS audience would. "Fixed via static code analysis, not a live browser pass" is a
  meaningfully weaker claim for this specific product's specific audience than it would be for a
  desktop-first B2B tool. I'd move this up in priority for an actual Playwright/live-device pass
  (the debrief redesign session already demonstrated this org can do exactly that kind of check — it's
  precedented, not a new ask) rather than leave it in "addressed" status indefinitely.

## 5. Other coherence findings from this pass (not previously flagged anywhere I could find)

- **The same "auth-check-before-existence-check" bug fixed in the debrief route is still live in its
  twin, the question route.** `BACKLOG.md`'s 2026-08-27 entry describes finding and fixing exactly this
  shape of bug in `app/api/interview/debrief/route.ts` (`assertSessionOwner(sessionId)` was called
  before the `!sessionId` presence check). Reading `app/api/interview/question/route.ts` today, it has
  the identical ordering:
  ```
  const { sessionId } = await req.json();
  const authCheck = await assertSessionOwner(sessionId);
  if (!authCheck.ok) return authCheck.response;
  if (!sessionId) { ... }
  ```
  This isn't a crash — `assertSessionOwner` with `sessionId === undefined` just returns a 404 "Session
  not found" instead of the more diagnosable 400 "sessionId is required" — but it's the same masked-
  error-message anti-pattern that was worth a dedicated fix note in the other file. Worth a quick
  follow-up pass since it's a two-line change and the precedent for fixing it already exists.
- **`docs/debrief-schema-migration.md` is more than "slightly stale" — it's three schema generations
  behind.** CLAUDE.md already flags it as "may be slightly stale," but reading it against the live
  `DebriefReport` interface in `lib/groq.ts`, it predates: the two-call scoring/synthesis split, and the
  entire "Coaching Cockpit" rework (`priority_risks`, `model_answers` with `your_quote`/`why_it_hurt`,
  `path_to_next_tier`, `confidence_rationale`, `question_walkthrough`). It still shows `hire_probability`
  living directly in `summary` next to `overall_impression` as if that were the intended shape, and its
  example `metrics` block (`"talk_to_listen_ratio": "72/28"`) doesn't match the current metrics format.
  Recommend either archiving it with a clear "historical — superseded by `lib/groq.ts`" banner, or
  deleting it now that `lib/groq.ts` is explicitly the source of truth per CLAUDE.md's own rule. Leaving
  it as-is risks a future session (human or agent) reading it as a target schema rather than a
  superseded plan.
- **The homepage founder-photo section is live with a placeholder, not flagged as a visible gap on the
  page itself.** PRD status calls this "🟡 Built" with the honest caveat that the real photo never got
  dropped in. That's fine as an internal status note, but worth a Product opinion: a gradient block
  where a "real face" trust element is supposed to be is exactly the kind of half-finished-looking
  surface the ICP-first redesign was otherwise trying to move away from (the whole point of that section
  was building trust with first-time candidates). I'd treat "ship the real photo or pull the section
  entirely" as a genuine open decision, not a background task — a visibly empty trust element can read
  worse than not having attempted one.
