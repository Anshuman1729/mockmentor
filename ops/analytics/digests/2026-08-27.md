## 2. Correctness

No dead or unreachable `track()` calls found — every call site I traced is on a path that actually executes given its precondition (auth check passed, form step valid, etc.), and every property in the code matches what BACKLOG.md/CLAUDE.md claim it sends. Two things worth flagging as correctness risks, not confirmed bugs:

- **`session_completed`'s `interview_depth`/`round_type` inherits a known, already-self-flagged inconsistency.** `app/api/interview/debrief/route.ts` and `app/api/interview/question/route.ts` each maintain their own round-type-normalization map, and they disagree on legacy `"screening"`/`"technical"` values: the debrief route treats them as their own round types (5 and 8 questions), the question route folds both into `technical_screen` (5 questions). This was already caught and documented in BACKLOG.md (not my find) rather than silently left in place — but it means `interview_depth` and any round-type segmentation on old in-flight sessions carries a real, undetermined amount of noise until someone decides which behavior is actually intended. Flagging because it directly affects "which round types have the highest drop-off" — one of the questions this taxonomy is supposed to answer.
- **`hire_probability`/raw signal scores never leak into any event.** Checked every `track()` call site by hand — `session_completed` only ever sends the bucketed `recommendation` string, lowercased/snake_cased. This is the one Article II-adjacent thing in scope for this review (non-negotiable rule against exposing that number anywhere, including to a third-party vendor) and it holds.

## 3. Naming consistency

Event names are consistently `snake_case`, consistently `noun_verb` in structure (`session_started`, `cta_clicked`, `debrief_generation_failed`) — but **tense is not consistent across the set**:

- Past tense (the majority): `landing_page_viewed`, `cta_clicked`, `session_started`, `session_completed`, `sign_up_completed`, `sign_in_completed`, `debrief_generation_failed`, `drill_used`.
- Present tense (the outlier): `basics_submit`, `personalisation_submit`, `jd_submit` — should structurally be `basics_submitted`/`personalisation_submitted`/`jd_submitted` to match the rest of the set. Minor, but it's exactly the kind of inconsistency that turns into a recurring "wait, was it `_submit` or `_submitted`?" query-authoring tax once someone else is writing Mixpanel queries against this taxonomy — worth a one-line fix before Junior/Senior Analyst seats exist and have to memorize the exception.
- `personalisation_submit` also uses British spelling where the rest of the identifiers (and most of this codebase's UI copy, e.g. "Personalize it" in `SetupForm.tsx`'s own step title) use American spelling. Small, but the same "exception a new analyst has to memorize" cost applies.

Property naming is clean and consistent — `snake_case` throughout, no camelCase leaking in from the TS call sites, no property that means two different things under the same name across events.

**`is_test` filtering is inconsistent, and this is the most concrete gap in the review.** It's applied correctly on `session_started` (quick-test route hardcodes `is_test: true`) and `session_completed` (conditioned on `round_type === 'quick_test'`). It is **not applied at all** to:
- `debrief_generation_failed` — the quick-test route's whole documented purpose is exercising the real failure path (BACKLOG.md: "Real Groq API call, real DB rows... seeing the actual failure... is the point of this route"). If a quick-test run hits a real failure, it fires `debrief_generation_failed` with zero indication it was a test, indistinguishable from a real user's failed session in any `reason`-code breakdown.
- `drill_used` — the drill route has no awareness of whether the session it's scoring against is `quick_test` at all; nothing stops a test drill run from polluting real `drill_used` counts.

Neither is currently exercised in a way that would materially skew numbers yet (quick-test is "not yet used for a real test run" per BACKLOG.md, and drill usage volume is presumably still low), but both are real gaps against the stated intent ("still filterable out of real funnel analysis") and worth closing before either route sees real traffic.

## 4. Identity linking (`user_email` → Clerk `userId`)

Applied consistently. `lib/analytics.ts`'s `track()`/`setProfile()` always take Clerk's `userId` as `distinct_id`, never `user_email`, with `setProfile()` mapping the email to the Mixpanel-native `$email` property instead — this is the correct way to keep a human-readable identity without fragmenting the profile on email changes. `lib/analytics-client.ts`'s `identifyClient()` takes the same `userId`, and `MixpanelProvider` calls it on every signed-in page load (not just first login), which correctly prevents a returning-but-already-logged-in visitor's client events from drifting onto a fresh anonymous device id. `SetupForm.tsx` also calls `identifyClient()` directly, redundantly-but-safely, immediately before the `sign_up_completed`/`sign_in_completed` event on the auth-redirect-return render — a reasonable defensive call given how load-bearing correct attribution is for that one event.

One real edge case not resolved anywhere: `session_completed` uses `userId ?? session.user_email` as its `distinct_id`, and `debrief_generation_failed` uses `userId ?? "unknown"`. Both fall back away from `userId` if `auth()` doesn't resolve one — which would put that one event on a different identity than every other event in the same user's funnel (a real profile-fragmentation risk, exactly the failure mode the whole `userId`-over-`user_email` switch was meant to prevent). I didn't find a live case that would trigger this fallback (both routes require `assertSessionOwner` to pass first, which should already guarantee a resolved `userId`), so this reads as defensive code for a case that may never fire — but it's worth someone confirming that assumption rather than leaving it as an untested "should never happen."

## 5. Can this taxonomy actually answer the funnel questions it's meant to?

Walking each stated example question against the actual instrumented events:

- **"Landing → signup conversion rate"** — answerable. `landing_page_viewed` → `cta_clicked` → `basics_submit`/`personalisation_submit`/`jd_submit` → `sign_up_completed` gives every intermediate step, and `cta_location` lets you segment which entry point actually converts. No gap.
- **"Session-start → completion rate"** — answerable via `session_started` → `session_completed`, and the addition of `debrief_generation_failed` (this session, 2026-08-27, per BACKLOG.md) closes what was previously a real hole: before that fix, any exception in the debrief route produced *zero* analytics signal, making a backend failure indistinguishable from a user just closing the tab. That fix is real and closes a genuine gap in this exact question.
- **"Which round types have the highest drop-off"** — partially answerable, with the caveat in Section 2: `round_type` is present on `session_started`/`session_completed`, but the two normalization maps disagreeing on legacy values means any analysis mixing old and new sessions carries unquantified noise until that's resolved.
- **A gap not called out elsewhere**: there is no event between `session_started` and `session_completed`/`debrief_generation_failed` — nothing marks "a question was skipped" or "the user abandoned mid-interview without ever hitting the debrief endpoint" (e.g. closed the tab after 2 of 5 questions). Today, mid-session abandonment is invisible to this taxonomy — it only shows up as a `session_started` with no matching `session_completed` and no matching `debrief_generation_failed`, which conflates "actively gave up" with "still in progress" and with any client-side failure that never reaches the server at all (e.g. a JS error that stops the interview UI without a network call). This is a real hole in "which round types have the highest drop-off," since drop-off within a round is the harder and more useful question, not just completion rate.

## 6. Trust — what's confirmed live vs. code-complete only

This is the part of the mandate ("whether the underlying data can even be trusted for that question") that matters most right now, and BACKLOG.md is candid about it rather than overclaiming:

- **Confirmed live**: `session_started` — explicitly verified via a Vercel log export showing a real event landing after the `MIXPANEL_TOKEN`-carrying deploy went out (BACKLOG.md, 2026-08-26 entry). This is the one event in the whole taxonomy with an actual "it really works" citation rather than "the code looks right."
- **Code-complete, not verified live**: `session_completed`, `drill_used` (both flagged as needing "one real pass each" in the same entry), and — a larger unverified batch — **all six client-side events added in the 2026-08-27 acquisition-funnel pass** (`landing_page_viewed`, `cta_clicked`, `basics_submit`, `personalisation_submit`, `jd_submit`, `sign_up_completed`/`sign_in_completed`), plus `session_completed`'s two new properties (`interview_depth`, `session_duration_sec`). BACKLOG.md's own status line for that whole pass: "Not yet verified live... Needs a real click-through (visit → CTA → all 3 wizard steps → sign-up → finish an interview) against a deployed build with `NEXT_PUBLIC_MIXPANEL_TOKEN` set."
- Practically, that means **most of the funnel this digest just validated as "answerable in principle" (Section 5) has never actually been confirmed to produce real rows in Mixpanel** — only `session_started` has. Until that click-through happens against a real deployed build, any funnel report built from this data is trusting code review, not observed behavior. I'd treat every number this taxonomy could produce today as provisional until that verification pass runs — this is the single highest-priority action item out of this review, ahead of the naming/tense cleanup above.
- `MIXPANEL_TOKEN` is confirmed added to `.env.local` for local dev; BACKLOG.md flags it as "still needed" in Vercel's production env vars as of the last entry I could find — worth confirming this is actually set in prod before trusting any of the above numbers, since a missing token fails open (silently drops events) rather than erroring, which is the right design call for not breaking the product but means a misconfigured prod env would produce a taxonomy that *looks* complete in code review while quietly producing zero real events.
